# Письмо хостеру — исходящий сетевой канал сервера 159.194.254.52

Замер проведён 2026-09-10, 02:14–02:23 UTC, на самом сервере (`matshkola-01`, Ubuntu 24.04.4,
ядро 6.8.0-139-generic), инструментом `ops/diagnostika_kanala.py`.

## Что наблюдаем

**1. IPv6 у сервера нет вообще — ни адреса, ни маршрута.**

```
ip -6 addr show scope global
  → (пусто; есть только fe80::/64, локальный link-local)
ip -6 route show
  → (пусто; ни одной глобальной записи, только связанный link-local)
```

Любое обращение по IPv6 падает мгновенно с `Network is unreachable` (ядро отказывает
раньше, чем уходит хоть один пакет) — это не таймаут и не потеря пакетов, это отсутствие
адресации на интерфейсе. Проверено на трёх независимых адресах, включая один без DNS
(`1.1.1.1`, у него просто нет IPv6-формы для сравнения):

```
ip -6 route get 2001:67c:4e8:f004::9   # api.telegram.org
  → RTNETLINK answers: Network is unreachable
ip -6 route get 2a06:98c1:3122:8000::6 # openrouter.ai
  → RTNETLINK answers: Network is unreachable
```

Замер 600 проб `curl` (три адреса × два протокола × 100 проб, таймаут 3 с) даёт по IPv6
**0 успехов из 300** (100 на каждый из трёх адресов) — 0.0%. Вопрос: сервер должен получить
IPv6-адрес и маршрут по умолчанию, или IPv6 на этом тарифе не предоставляется вовсе?

**2. Системный DNS-резолвер сервера указывает на адрес из диапазона, зарезервированного
под тестирование сетевого оборудования (RFC 2544), а не под резолвинг.**

```
cat /etc/resolv.conf
  → nameserver 198.18.18.18
```

Диапазон `198.18.0.0/15` зарезервирован под замеры производительности сетевого
оборудования (RFC 2544) и не должен встречаться в продуктивной адресации. На момент замера
этот резолвер отвечает и его ответы совпадают с ответами `8.8.8.8` для обоих проверенных
имён (`api.telegram.org`, `openrouter.ai`), по записям A и AAAA:

```
dig +short A api.telegram.org            → 149.154.166.110
dig +short @8.8.8.8 A api.telegram.org   → 149.154.166.110   (совпадает)
dig +short A openrouter.ai               → 8.47.69.6, 8.6.112.6
dig +short @8.8.8.8 A openrouter.ai      → 8.47.69.6, 8.6.112.6   (совпадает)
```

Вопрос: почему `/etc/resolv.conf` указывает на адрес из тестового диапазона RFC 2544, а не
на резолвер хостера или публичный резолвер? Файл написан `cloud-init` (`manage-resolv-conf:
true`) при выдаче сервера — это значение пришло из конфигурации хостера, не выбрано нами.

**3. Исходящий IPv4-канал на момент замера — стабилен, 100% проб прошли.**

Замер 08.09 (ручные пробы) фиксировал прохождение `curl -4` примерно в 1 случае из 2–3.
Текущий замер 2026-09-10 (600 проб, три адреса × два протокола × 100 проб каждый,
таймаут 3 с на пробу) этого не подтверждает — IPv4 прошёл на 100%:

```
api.telegram.org   -4   100/100 ok (100.0%)  медиана=0.251s  худшие 10%=0.389s
openrouter.ai       -4   100/100 ok (100.0%)  медиана=0.109s  худшие 10%=0.119s
1.1.1.1              -4   100/100 ok (100.0%)  медиана=0.108s  худшие 10%=0.122s
```

Вопрос: расхождение между ручным замером 08.09 (частые обрывы IPv4) и автоматическим
замером 10.09 (0 обрывов из 300 проб IPv4) — было ли на стороне хостера событие между этими
датами (перенос, изменение маршрутизации, инцидент), которое объясняет улучшение? Просим
проверить по своим логам исходящий трафик с `159.194.254.52` за период 2026-09-08 —
2026-09-10 на предмет потерь пакетов или флаппинга маршрута.

## Чем замерено

Скрипт `ops/diagnostika_kanala.py` (в репозитории), запуск:

```
python3 diagnostika_kanala.py --probes 100 --timeout 3 --outdir /tmp/kanal-diagnostika-run1
```

Каждая проба — отдельный вызов `curl -4|-6 -sk -o /dev/null --max-time 3 -w '%{http_code}
%{time_total}' https://<адрес>/`, результат дописывается на диск построчно (JSONL) сразу
после получения, не накапливаясь в памяти. Сырые данные (600 строк) лежат на сервере в
`/tmp/kanal-diagnostika-run1/`.

## Чего этот замер НЕ проверяет

Входящий канал (сервер как получатель соединений — ничего здесь не слушает входящие),
поведение под нагрузкой (замер шёл без параллельной нагрузки от бота/сайта) и разницу
между ночью и днём — это один прогон, одна точка во времени, 2026-09-10 02:14–02:23 UTC.
